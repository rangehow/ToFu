## How it was taken (read-only on the old path)

- Old refs were listed with `git --no-optional-locks for-each-ref`. Worktrees were listed by reading `.git/worktrees/*/{gitdir,HEAD}`
  files directly; `git worktree list` was not used because it can prune or lock. A single `touch` probe of the old root created no file,
  which confirms the path is write-protected. Afterwards the old `HEAD`, `index` and per-worktree index mtimes were unchanged.
- The old repo and this repo share one object store lineage: all 7,218 old refs and their objects were already present
  here when the repo was copied. The only divergence is `eval/opencode-glm53-tb21`: old `d12cd290ae` is an ancestor of the current
  `bf154075a3`. So "fetch" needed no network or object copy. `recovered/*` refs were created with `git update-ref` in **this**
  repo, pointing at the same SHAs. `git rev-list --objects --missing=print` over every recovered tip reports 0 missing objects.
- Containment test per ref: `merge-base --is-ancestor` against the branch. Otherwise there is a line-level content test: every added line
  of `merge-base..tip` is looked up in the branch's version of the file. That classifies a ref as content-landed, mostly-landed
  (≤5% of added lines missing) or not landed. History was rebuilt on 2026-10-22: the new root `91b4c7e205` has the same tree as old
  `fabc9d804f`, now `backup/pre-rewrite-20261022`. Older refs were therefore tested against `fabc9d804f` as well.
- Uncommitted work: for each live worktree, its index was copied to `/tmp`. Then `git add -A` ran with `GIT_DIR` set to this repo,
  `GIT_WORK_TREE` set to the old checkout and `GIT_INDEX_FILE` set to the copy, which writes objects only into this repo.
  The result was committed with `commit-tree` on the worktree's own HEAD. Every changed path was re-hashed from the old
  worktree bytes (`git hash-object --no-filters`) and compared with the blob in the commit. Mismatches: 0. A sha256 of
  `git diff --binary HEAD..commit` is recorded as `diffsha`.
- The first 91 worktrees were captured with plain `git add -A` (capture.sh). On the shared FUSE mount git's untracked walk is
  serial (one ~1–2.5 s round trip per directory or file), so walks overran a 1,800 s bound. The rest were captured with an equivalent
  split (scan2.py): `git add -u` (tracked paths, git's parallel preload), a parallel listing of every directory that holds tracked
  files, `git check-ignore --stdin` over the entries absent from the index, then `git add -A` of the non-ignored ones. It was validated
  against three worktrees already captured by `git add -A` (two dirty with new, modified and deleted files, one clean): identical trees
  (`d8288c5c71`, `cf134d2d87`, `58d86e8c4c`).
